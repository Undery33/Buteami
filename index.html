04 — CONTINUOUS DELIVERY

코드의 변화가,
화면의 변화로.

지금 보고 있는 웹사이트도
우리의 배포 파이프라인을 통해 전달됩니다.

main 브랜치 변경 확인 · 5분 주기
  1. feature/web
    + 새로운 가능성
    1
    DEVELOP

    아이디어를 코드로

    Client PC에서 웹 화면을 개선하고
    feature/web에 변경 사항을 기록합니다.

  2. Pull Request
    ↗feature/web → main
    ✓ 변경 내용과 검증 기록
    2
    REVIEW & MERGE

    변경의 이유까지 남기고

    PR에 개선 내용과 검증 결과를 작성하고
    main에 병합해 배포의 출발점을 만듭니다.

  3. Jenkins pipeline
    01 Checkout →
    02 Build & Push →
    03 Deploy ↗
    3
    BUILD & PUSH

    자동화된 흐름을 따라

    Jenkins가 main의 변경을 확인하면
    BuildKit으로 이미지를 빌드해 GHCR에 저장합니다.

  4. Kubernetes
    ⎈
    NGINX부티미 웹 서비스
    코드의 변화 → 화면의 변화
    4
    DEPLOY

    새로운 화면을 만납니다

    Kubernetes가 웹 서비스 이미지를 업데이트하고
    롤아웃 상태를 확인합니다.

변경의 과정도 프로젝트의 일부입니다.
코드와 개선 이력은 GitHub에서 확인할 수 있습니다.
